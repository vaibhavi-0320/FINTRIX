# Datasets and data

Fintrix keeps **user data**, **synthetic training/evaluation data** and **test fixtures** strictly separate. No synthetic record is ever written into the application database. Demo listings created by `npm run demo:seed` are real testnet transactions and are flagged `is_demo = true` in the database and labelled "Demo listing" in the UI.

## 1. Synthetic accounts-receivable ledger (risk model)

| | |
|---|---|
| **Type** | Synthetic (generated). Contains no real companies, people or transactions. |
| **Generator** | `ml/generate_dataset.py` (version 1.0.0), seeded (`--seed 42`) and fully reproducible |
| **Size** | 7,862 invoices, 600 buyers, issue dates 2023-01-01 → 2025-12-31 |
| **Location** | `ml/data/synthetic_ar_ledger.csv` (git-ignored; regenerate with `npm run ml:data`) |
| **Licence** | Generated by this project; same licence as the repository (MIT) |

### Schema
| Column | Type | Description |
|---|---|---|
| invoice_id | string | `SYN-000000` |
| buyer_id | string | `BUYER-0000` |
| issue_date | date | ISO date |
| due_date | date | issue_date + terms |
| settled_date | date | due_date + days_late |
| amount_usd | float | invoice amount |
| terms_days | int | one of 15, 30, 45, 60, 90 |
| days_late | int | 0 if paid on time |
| is_late | int | label: 1 if days_late > 0 |

### Generative assumptions
Each buyer has a latent reliability `z ~ N(0,1)` and a typical invoice size (log-normal, median about $3k). For each invoice:
`P(late) = sigmoid(-0.55 − 1.1·z + 0.25·(ln amount − 8) + 0.012·(terms − 30) + ε)`, ε ~ N(0, 0.6).
Days late follow `1 + Gamma(1.5, 8·e^(−0.4z))`. The late rate is about 43%.

### Preprocessing
`ml/train_risk_model.py` derives buyer-history features using only invoices settled before each invoice's issue date (leakage-safe), fills missing history with training-set means, standardises features, and splits by time (train < 2025-07-01, 6,562 rows; test 1,300 rows).

### Why synthetic
We looked for a public, invoice-level payment dataset with a verifiable licence:
- The widely circulated **IBM "Accounts Receivable" sample** (`WA_Fn-UseC_-Accounts-Receivable.csv`) is itself simulated data from IBM Watson Analytics, according to its documentation in the `data1135` R package ([rdrr.io](https://rdrr.io/github/bcBusinessStats/data1135/man/accts_recv.html)). We could not find a statement of its licence. Using it would add licence risk without adding real-world signal, so it is **not used**.
- Consumer credit datasets (e.g. UCI "Default of Credit Card Clients") model a different problem (individual card default) and lack invoice terms.

**Implication:** the risk model's metrics measure recovery of the documented generator, not real-world performance. See [AI_ML_DOCUMENTATION.md](AI_ML_DOCUMENTATION.md).

## 3. Retrieval evaluation set
20 hand-written questions, each labelled with the knowledge article that should answer it (`tests/backend/knowledge-eval.test.ts`).

## 4. Test fixtures
`tests/fixtures/` is generated by `npm run fixtures` (`scripts/make-fixtures.mts`):
- `invoice-sample.pdf` / `.png`: a synthetic invoice for fictional companies, with known values in `sample.json`
- `scanned-no-text.pdf`: a PDF without a text layer
- `fake.pdf`: HTML disguised as a PDF (upload-validation test)

## 5. Knowledge base
`knowledge/*.md`: 17 articles written for this project describing the implemented system. These are the assistant's only Fintrix-specific source.

## 6. Application data (Postgres)
| Table | Contents | Retention / deletion |
|---|---|---|
| users | wallet address, optional display name, role | kept |
| sessions | SHA-256 of token, user-agent, expiry | expire after 7 days; revocable |
| auth_challenges | one-time sign-in nonces | expire after 5 min |
| documents | uploaded files (bytea), hash, extracted text | owner can delete unless they back a listed invoice |
| extractions | extracted + reviewed fields, confidence, issues | deleted with the document |
| invoices | invoice facts, terms, status mirrored from chain, risk, duplicate flags, `is_demo` | drafts deletable; listed ones are permanent (on-chain) |
| chain_transactions | prepared/submitted tx hashes and outcomes | kept (audit trail) |
| conversations, messages | assistant history | user can delete conversations |
| kb_documents, kb_chunks | knowledge base + embeddings | rebuilt from `knowledge/` |
| rate_limits | fixed-window counters | overwritten each window |
| audit_log | security events without secrets | kept |

Indexes cover the common lookups: status, seller, investor, buyer name, document hash, user-scoped lists and full-text search.

## Backup and recovery
- **Production (managed Postgres such as Neon or Supabase):** enable the provider's automated daily backups and point-in-time recovery. Take a logical backup before each deploy that adds a migration: `pg_dump --format=custom "$DATABASE_URL" > fintrix-$(date +%F).dump`. Restore with `pg_restore --clean --if-exists -d "$DATABASE_URL" fintrix-YYYY-MM-DD.dump`.
- **Local (PGlite):** the database is the directory `.data/pglite`. Stop the server and copy the directory to back it up; delete it to reset (migrations recreate the schema on the next start).
- **Recovery from the chain:** invoice status is mirrored from the contract. After a restore, open an invoice and press **Sync** (`POST /api/invoices/:id/reconcile`) to re-read its on-chain state.
- **Migrations** (`backend/db/migrations/*.sql`) are applied automatically and recorded in `schema_migrations`; they are forward-only.
