# AI and Machine Learning in Fintrix

Fintrix uses AI and ML in four places. This document covers what each one does, how it was built and evaluated, and its limitations. All numbers come from scripts in this repository and can be reproduced.

| Component | Type | Needs a key? | Code |
|---|---|---|---|
| Invoice extraction | LLM (Claude) **or** local OCR + rules | Claude: `ANTHROPIC_API_KEY`. Local: none | `backend/modules/documents/` |
| Assistant | LLM + retrieval-augmented generation | `ANTHROPIC_API_KEY` | `backend/modules/assistant/` |
| Late-payment risk | Logistic regression (trained) | none | `ml/`, `backend/modules/ml/risk.ts` |
| Duplicate detection | Rules + fuzzy similarity (evaluated) | none | `backend/modules/ml/duplicates.ts` |

**Principle:** AI output is never treated as verified. Extracted invoice data needs human review. Risk and duplicate signals are explanations, not decisions. No AI output can trigger a blockchain transaction, because every transaction needs the user's wallet signature.

## 1. Invoice extraction

### Pipeline
1. **Upload.** PDF/PNG/JPEG/WebP up to 4 MB. The type is detected from magic bytes, the file's SHA-256 is computed, and the file is stored privately.
2. **Engine selection** (`EXTRACTION_PROVIDER=auto`). Claude is used when `ANTHROPIC_API_KEY` is set; otherwise the local engine.
3. **Extraction.**
   - **Claude** (`claude-opus-5-5` by default): the PDF (native document input) or image is sent with an instruction to copy values exactly and use `null` when absent. Output is constrained by a JSON schema (structured outputs), including a confidence score of 0–1 for each field and an `isInvoice` flag. Text inside the document is explicitly treated as data, not instructions.
   - **Local:** pdf.js reads a PDF's text layer and tesseract.js OCRs images. A rule-based parser (`textRules.ts`) then finds labelled fields (invoice no., dates, totals, tax, bill-to, line items), detects the currency, and derives due dates from "Net N" terms. Confidence is heuristic: higher for fields found on the same line as their label, and reduced by 15% for OCR text. Scanned PDFs (no text layer) are rejected with a clear message.
4. **Deterministic validation** (`schema.ts`, for both engines): required fields, valid ISO dates, due ≥ issue, ISO 4217 currency, subtotal + tax = total, line items summing correctly, quantity × unit price = amount, and low-confidence warnings below 0.6.
5. **Persistence.** Results go in the `extractions` table (fields, confidence, issues, engine).
6. **Human review.** The user corrects the fields. `PUT /api/extractions/:id/review` re-validates them. Only a reviewed extraction without errors can become an invoice (`POST /api/extractions/:id/invoice`), and listing it on-chain needs a further wallet signature.

### Extracted fields
Invoice number, issue date, due date, issuer (name, address, tax ID), recipient (name, address, tax ID), currency, subtotal, tax, total, and line items (description, quantity, unit price, amount).

### Measured results
On the synthetic fixtures (`tests/fixtures`, generated by `scripts/make-fixtures.mts`), the local engine extracts **every field exactly** from both the PDF (`local:pdf-text`, ~6 s cold) and the PNG (`local:tesseract-ocr`, ~5 s). This is asserted in `tests/backend/documents.test.ts`. It shows the pipeline works end to end on a conventionally laid-out invoice; **it is not an accuracy benchmark** across real-world layouts.

**Claude extraction has not been measured** in this repository because no API key was available during development. Its code path is covered by unit tests with the provider stubbed out. Once a key is configured, re-run the extraction on your own invoices before relying on it.

### Limitations
- The local rules work best on invoices with explicit labels ("Invoice No", "Due Date", "Total"). Unusual layouts, multi-column tables and handwriting will produce missing or wrong fields. That's what review is for.
- The local engine can't read scanned PDFs. Upload an image instead, or use Claude.
- The issuer name from the local engine comes from the first line of the document (confidence 0.4) unless a "From/Seller" label exists.

## 2. Assistant (RAG)

### How it answers
1. **Knowledge base:** 17 Markdown articles in `knowledge/` (product, architecture, guides, finance, Stellar, contract, transaction lifecycle, AI/ML, security, FAQ, troubleshooting, business model, limitations, glossary, judge summary).
2. **Ingestion** (`knowledge.ts`): front matter is parsed, the text is split along headings into chunks of at most ~1,200 characters (106 chunks), each chunk is embedded, and it's stored in `kb_chunks` with a pgvector embedding and a Postgres `tsvector`. Ingestion runs at startup and skips unchanged files by checksum; `npm run kb:ingest -- --force` re-indexes.
3. **Embeddings:** `local` = all-MiniLM-L6-v2 (384-d, quantised, on-device via transformers.js, no key). `voyage` = voyage-3.5-lite (512-d, API; recommended on Vercel). `none` = keyword search only.
4. **Hybrid retrieval:** cosine-similarity top-20 plus full-text top-20 (an OR query over stemmed terms), fused with reciprocal-rank fusion (k = 60). At most 2 chunks are kept per article, and the top 6 go to the model.
5. **Generation:** a provider-agnostic `LlmProvider` interface (`llm.ts`). The Anthropic implementation streams with the official SDK. The system prompt sets the facts about Fintrix, citation rules ([n]), the distinction between general knowledge and Fintrix-specific facts, no financial/legal/tax advice, and that the assistant can't perform actions. It also contains a screen-by-screen map of the Fintrix app with the exact button names (Connect Wallet, Simulation, Confirm fields & list on marketplace →, Simulate on Testnet ▷, View Details, FUND THIS INVOICE, REPAY INTO ESCROW, CLAIM REPAYMENT, Cancel listing, Mark as defaulted) and how the UI's Trust Score / Risk Level maps to the late-payment model, so directions match what the user sees. It instructs the model to treat `<sources>` and `<user_data>` as data (prompt-injection boundary). Chat runs at `effort: medium`, with server-side refusal fallback. Five audience styles are available (the in-app widget uses "app user").
6. **Page and personal context** (`context.ts`): the widget sends only *where* the user is (`view`, and the id of the deal on screen). The server then reads, fresh for every message: the XLM balance from Horizon, the user's invoices as seller and as investor, open marketplace listings (in full on Marketplace/Simulation/Dashboard), the last 8 Fintrix transactions and simulations, and — on the deal page — the open deal with its price, repayment, return, APY, days to due date, risk band, duplicate warnings and the actions available to this user, named as the UI's buttons. Visibility rules are the API's: another user's draft passed as `invoiceId` is silently ignored (tested). This is what makes "this invoice", "Pre-funding checklist" and "Detect red flags" answerable.
7. **Streaming and persistence:** answers stream over Server-Sent Events. Sources are sent first, then text deltas, then 2–3 suggested follow-up questions (parsed from a trailing tag that a streaming filter removes). Conversations and messages are stored per user.
8. **Failure behaviour:** if the AI is not configured or fails, the user gets the real error **plus the retrieved sources**. There is no canned fallback answer.

### Retrieval evaluation
`tests/backend/knowledge-eval.test.ts` runs 28 labelled questions (8 phrased like the app's own quick questions and buttons) against the real local embedding model and checks that the expected article is retrieved:

| Metric | Result |
|---|---|
| hit@3 | **0.93** (26/28) |
| hit@1 | 0.61 (17/28) |

hit@1 is lower because several articles legitimately answer the same question (e.g. FAQ vs. the seller guide). What the model receives is the top 6, so hit@3 is the more relevant measure. The test fails if hit@3 drops below 0.85.

**Answer quality with the real model has not been measured yet** (no API key during development). Behaviour is covered with a stub provider: streaming, citations, follow-up stripping, multi-turn context, page/deal/balance context, cross-user isolation, failure reporting (`tests/backend/assistant.test.ts`). Once `ANTHROPIC_API_KEY` is in `.env`, `npm run assistant:eval` runs `tests/backend/assistant-live.test.ts` against real Claude: next-step advice on the open deal (must name LIST ON MARKETPLACE), the deal's real price and repayment, the user's balance, Trust Score with citations, Simulate on Testnet, refusing to act ("fund this for me"), no personal financial advice, and a prompt-extraction attempt. Answers are printed for review. Normal test runs and E2E force the key empty so they never call the paid API.

## 3. Late-payment risk model

### Problem
Estimate, at listing time, the probability that an invoice is paid **after** its due date. Investors see it as a "late risk" indicator, with the top contributing factors explained in plain language.

### Data
There is no suitable public invoice-level payment dataset with a verifiable licence (see [DATASET_DOCUMENTATION.md](DATASET_DOCUMENTATION.md)), so the model is trained on a **reproducible synthetic ledger** (`ml/generate_dataset.py`, seed 42): 7,862 invoices from 600 fictional buyers. **The model therefore learns the generator's documented assumptions, not real-world behaviour.**

### Features (identical in Python and TypeScript)
| Feature | Meaning |
|---|---|
| `log_amount` | ln(1 + invoice amount in USD) |
| `terms_days` | days between issue and due date |
| `log_prior_count` | ln(1 + buyer's previous invoices with a known outcome) |
| `prior_late_rate` | share of those paid late (training mean if no history) |
| `prior_avg_days_late` | their average days late (training mean if no history) |
| `has_history` | 1 if the buyer has any prior outcome |

History features use only invoices **settled before** the current invoice's issue date, so there is no look-ahead leakage. In the app, history comes from repaid, settled or defaulted Fintrix invoices with the same buyer name; a default counts as 60 days late.

### Model and training
Standardised features followed by `LogisticRegression(C=1.0)` (scikit-learn 1.9.1). It was chosen for interpretability and because it ships as a small JSON file (`backend/modules/ml/models/risk-model.json`) that Node evaluates exactly. `tests/backend/ml.test.ts` checks parity with scikit-learn's probabilities on 8 held-out cases (difference < 1e-4).

### Evaluation (time-based split: train before 2025-07-01, test after; 1,300 test invoices, 43.4% late)
| Model | ROC AUC | PR AUC | Brier | Log loss | Accuracy@0.5 |
|---|---|---|---|---|---|
| **Logistic regression (deployed)** | **0.719** (95% CI 0.691–0.745) | 0.653 | 0.213 | 0.616 | 0.661 |
| Gradient boosting (capacity check) | 0.687 | 0.632 | 0.222 | 0.636 | 0.635 |
| Baseline: buyer's prior late rate | 0.706 | 0.636 | 0.220 | 0.742 | 0.660 |
| Baseline: constant base rate | 0.500 | 0.434 | 0.246 | 0.685 | 0.566 |

Calibration on the test set is reasonable in the populated bins (e.g. predicted 0.49 vs observed 0.52; predicted 0.68 vs observed 0.68). The full table is in `ml/reports/risk_model_report.json`.

### Honest interpretation
- The model clearly beats the constant baseline but **only modestly beats the simple prior-late-rate rule** in ranking (AUC 0.719 vs 0.706), though it is better calibrated (log loss 0.616 vs 0.742).
- **Every test-set buyer already had history** (`share_without_history = 0`). Performance on **new buyers**, which will be the common case on a young marketplace, **was not evaluated**. For them the score is driven by amount and terms only.
- Because the data is synthetic, these numbers say the pipeline can recover a known signal. They say nothing about real credit risk. The UI states this next to every score.

### Reproduce
```bash
py -m venv ml/.venv && ml/.venv/Scripts/python -m pip install -r ml/requirements.txt   # macOS/Linux: ml/.venv/bin/python
npm run ml:data     # ml/data/synthetic_ar_ledger.csv  (git-ignored)
npm run ml:train    # writes the model JSON, ml/reports/risk_model_report.json, parity_cases.json
```

## 4. Duplicate-invoice detection

### Problem
Double financing: the same receivable financed more than once, by the same or different sellers.

### Method
1. **On-chain hard block:** the escrow contract refuses a second active listing with the same document SHA-256.
2. **Off-chain flags** (`duplicates.ts`), computed whenever an invoice is created or edited:
   - `same_document` (high): identical file hash.
   - `same_number_and_buyer` (high): normalised invoice number equal (`INV-0042` = `#42`) and buyer name Jaro-Winkler ≥ 0.90 after normalisation (case, punctuation, legal suffixes such as Ltd/Limited/LLC).
   - `near_duplicate` (medium): same currency, buyer similarity ≥ 0.90, amount within 0.5%, issue dates ≤ 7 days apart.

### Evaluation (`npm run ml:eval-duplicates` → `ml/reports/duplicates_report.json`)
500 seeded synthetic pairs: 200 true duplicates (exact re-upload, rescan with name variants, reformatted number, re-issue with rounding and date shift) and 300 non-duplicates, including hard negatives (recurring monthly invoices with identical amounts, the same number from a different buyer, the same buyer with a different amount).

| Precision | Recall | F1 | TP | FP | FN | TN |
|---|---|---|---|---|---|---|
| 0.976 | 1.000 | 0.988 | 200 | 5 | 0 | 295 |

There were no false positives on the 81 recurring-monthly or 76 same-buyer/different-amount pairs. The 5 false positives came from "same number, different buyer" pairs where the generator happened to choose the same buyer name, so they are arguably genuine duplicates.

**Limitation:** recall of 1.0 is optimistic. The perturbations were designed by the same author as the rules. Real fraud (altered amounts, different buyer spellings, split invoices) will be harder.

## Provider architecture and keys
- Claude is accessed only from the server through the official `@anthropic-ai/sdk`. The key (`ANTHROPIC_API_KEY`) never reaches the browser.
- Chat uses the server-side refusal fallback (`fallbacks: "default"`), so a safety decline by the primary model is rerouted instead of returning nothing.
- To add another provider, implement `LlmProvider` (`streamChat`, `extractStructured`) and return it from `getLlm()`.
